## Authorization & lifecycle

All quotes are from the pinned `TDLibKit` 1.5.2-tdlib-1.8.66-022d6020 sources, root `~/Library/Caches/NotchGram/spm/checkouts/TDLibKit/Sources/TDLibKit`. NotchGram calls the `async throws` variants on `TDLibClient`, which subclasses `TDLibApi` (`Generated/API/TDLibApi.swift`). `Generated/API/TdApi.swift` declares the identical surface on `public final class TdApi` holding a `TdClient` and routing through its own `execute(query:completion:)` — an alternate, not what `TDLibClientManager` hands you.

Every auth request below returns `Ok` (except `getAuthorizationState` → `AuthorizationState`, `getMe` → `User`, `createPrivateChat` → `Chat`); stated once, not repeated per item.

### `setTdlibParameters` — exactly 14 parameters, no defaults

`TDLibApi.swift:119`. All 14 are non-defaulted Optionals, so **every call site must pass all 14** — Optional here means "encodable as null", not "omittable".

```swift
@available(iOS 13.0, macOS 10.15, watchOS 6.0, tvOS 13.0, *)
@discardableResult
public final func setTdlibParameters(
    apiHash: String?,
    apiId: Int?,
    applicationVersion: String?,
    databaseDirectory: String?,
    databaseEncryptionKey: Data?,
    deviceModel: String?,
    filesDirectory: String?,
    systemLanguageCode: String?,
    systemVersion: String?,
    useChatInfoDatabase: Bool?,
    useFileDatabase: Bool?,
    useMessageDatabase: Bool?,
    useSecretChats: Bool?,
    useTestDc: Bool?
) async throws -> Ok
```

`databaseEncryptionKey: Data?` is the one carrying the database encryption key — "Encryption key for the database. If the encryption key is invalid, then an error with code 401 will be returned". `useTestDc: Bool?` is NotchGram's test-DC switch. `useChatInfoDatabase` implies `use_file_database`; `useMessageDatabase` implies `use_chat_info_database` (per the field doc comments).

**Names that do not exist here:** there is no `TdlibParameters` struct (the parameters are flat on `SetTdlibParameters`), no `authorizationStateWaitEncryptionKey` case, and no `checkDatabaseEncryptionKey` request — grep over `Generated/Models/` returns nothing for either. `setDatabaseEncryptionKey(newEncryptionKey: Data?) async throws -> Ok` does exist (`TDLibApi.swift:799`), for rekeying after auth.

```swift

```
Doc comment: "This is an offline method. For informational purposes only. Use updateAuthorizationState instead to maintain the current authorization state. Can be called before initialization." NotchGram should drive state from the update stream, not poll this.

### `Error` — TDLibKit's type shadows `Swift.Error`

`Generated/Models/Error.swift`:

```swift
public struct Error: Codable, Equatable, Hashable, Swift.Error {
    public let code: Int
    public let message: String
}
```

It conforms to `Swift.Error`, so inside any file that imports TDLibKit, unqualified `Error` means this struct — generated code writes `Swift.Error` explicitly everywhere (`Result<Ok, Swift.Error>`). NotchGram's own `throws` code must do the same or risk silently constraining a generic to this struct. Doc note: "If the error code is 406, the error message must not be processed in any way and must not be displayed to the user."

How it reaches you (`TDLibApi.swift:31051`) — the async `run` tries decoding the reply as `DTO<Error>` first and resumes with `.failure(error.payload)`; a thrown non-`Error` is wrapped as `Error(code: 500, message: any.localizedDescription)`:

```swift
private final func run<Q, R>(query: Q) async throws -> R where Q: Codable, R: Codable {
    let dto = DTO(query, encoder: self.encoder)
    return try await withCheckedThrowingContinuation { continuation in
        do {
            try self.send(query: dto) { result in
                if let error = try? self.decoder.decode(DTO<Error>.self, from: result) {
                    continuation.resume(with: .failure(error.payload))
                } else {
                    let response = self.decoder.tryDecode(DTO<R>.self, from: result)
                    continuation.resume(with: response.map { $0.payload })
                }
            }
        } catch let err as Error {
            continuation.resume(with: .failure(err))
        } catch let any {
            let err = Error(code: 500, message: any.localizedDescription)
            continuation.resume(with: .failure(err))
        }
    }
}
```
So every `try await` on these requests throws `TDLibKit.Error` — `catch let e as TDLibKit.Error { e.code }` is the whole error-handling contract. `execute` additionally throws `Error(code: 404, message: "Empty response from TDLib")`.

### Client lifecycle — `TDLibClientManager.swift` (191 lines, not generated)

Three facts from this file that the request list does not name but that govern NotchGram's shutdown path:

1. **`closeClients()` busy-waits.** Documented "This is a blocking method", called from `deinit`:
```swift
public func closeClients() {
    for client in self.clients.values {
        try? client.close(completion: { _ in })
    }

    while (!self.clients.isEmpty) {}
}
```
The spin pegs a core until every client reports closed. The doc comment recommends calling it manually on `willTerminateNotification` "Otherwise, client data may be lost."

2. **Teardown is driven by the auth state machine.** A client is removed from `clients` only when the receive loop sees the closed state — this is the sole exit condition for the spin above:
```swift
private func checkClosedUpdate(_ dict: [String: Any]) -> Bool {
    if let state = dict["authorization_state"] as? [String: Any],
       (state["@type"] as? String) == "authorizationStateClosed" {
        return true
    }
    return false
}
```

3. **`createClient` self-activates and the API is explicitly unstable.** It sends `getOption("version")` to start the update flow, and the initializer carries `#warning("Breaking changes may be introduced to TDLibClientManager without major version bump.")`:
```swift
public func createClient(updateHandler: @escaping (Data, TDLibClient) -> Void) -> TDLibClient {
    let newClient = TDLibClient(updateHandler: updateHandler, logger: self.logger)
    self.clients[newClient.id] = newClient
    try? newClient.send(query: DTO(GetOption(name: "version")), completion: { _ in })
    return newClient
}
```
The manager owns one `td_receive(10)` loop on `receiveQueue` for all clients, hands decode work to `queryQueue`, and dispatches per-client updates on `client.updateHandlerQueue` — matching NotchGram's singleton-`TDLibClientManager`, one-client-id-per-account invariant.

### Naming deltas — what does NOT exist under the name you expect

### `getChatHistory`

## Files, media, download/upload

### Naming divergences (read these first)

- **`uploadFile` does not exist.** The upload request is `preliminaryUploadFile`; its canceller is `cancelPreliminaryUploadFile(fileId:)`, **not** `cancelUploadFile`. A case-insensitive grep for `uploadFile` across `TDLibApi.swift` matches only those two.
- **`downloadFile` parameter labels are alphabetical, not TL order.** TL declares `file_id, priority, offset, limit, synchronous`; Swift is `(fileId:limit:offset:priority:synchronous:)`. Getting this wrong is a compile error, so it is worth copying literally.
- **`getRemoteFile` is `(fileType:remoteFileId:)`** — `fileType` comes first in Swift, while TDLib declares `remote_file_id` first.
- **File-id stability, exactly as documented.** `File.id` carries only `/// Unique file identifier` — the sources make **no** lifetime claim about it, and grepping `File.swift`/`LocalFile.swift`/`RemoteFile.swift`/`InputFile.swift` for "no longer valid", "becomes invalid", "valid only", "TDLib instance" returns nothing. The only stability guarantees written down are on the *remote* side: `RemoteFile.id` — "Can be used by the current user across application restarts or even from other devices"; `RemoteFile.uniqueId` — "the same for the same file even for different users and is persistent over time". Treat `File.id` as session-scoped by absence of a guarantee, and persist `remote.id` / `remote.uniqueId` instead.

```swift
    private func queryResultAsync(_ result: Data) {
        self.queryQueue.async { [weak self] in
            guard
                let `self` = self,
                let json = try? JSONSerialization.jsonObject(with: result, options:[]),
                let dictionary = json as? [String:Any]
            else {
                return
            }
            
            let clientId = dictionary["@client_id"] as? Int32 ?? 1
            if let extraStr = dictionary["@extra"] as? String {
                if let client = self.clients[clientId] {
                    client.completionHandler(extra: extraStr, result: result)
                }
            } else {
                if let client = self.clients[clientId] {
                    client.updateHandlerQueue.async {
                        client.updateHandler(result, client)
                    }
                }
            }
            
            if self.checkClosedUpdate(dictionary) {
                self.clients.removeValue(forKey: clientId)
            }
        }
    }

    private func checkClosedUpdate(_ dict: [String: Any]) -> Bool {
        if let state = dict["authorization_state"] as? [String: Any],
           (state["@type"] as? String) == "authorizationStateClosed" {
            return true
        }
        return false
    }
}
```

**Analysis (not stated in the file): `deinit → closeClients()` cannot terminate.** Swift zeroes `weak` references before `deinit` runs, so by the time `closeClients()` spins on `while (!self.clients.isEmpty) {}`, both `[weak self]` closures (the receive loop and `queryResultAsync`) see `self == nil` — the loop `break`s and `queryResultAsync` returns early, so `clients.removeValue` is never reached and the spin never ends. NotchGram must call `closeClients()` **explicitly while the manager is still strongly held** (as the doc comment hints) and must never let the manager fall out of scope with live clients. Even in the happy path the wait is a 100%-CPU spin taking a `pthread_rwlock` read lock every iteration.

### `TDLibApi.run(query:)` — the async bridge

Both overloads are `private final` at `Generated/API/TDLibApi.swift:31025-31070` (bottom of the file). NotchGram never calls them directly; every `async throws` request funnels through the second one.

```swift
    private final func run<Q, R>(
        query: Q,
        completion: @escaping (Result<R, Swift.Error>) -> Void)
        where Q: Codable, R: Codable {

        let dto = DTO(query, encoder: self.encoder)
        do {
            try self.send(query: dto) { [weak self] result in
                guard let strongSelf = self else { return }
                if let error = try? strongSelf.decoder.decode(DTO<Error>.self, from: result) {
                    completion(.failure(error.payload))
                } else {
                    let response = strongSelf.decoder.tryDecode(DTO<R>.self, from: result)
                    completion(response.map { $0.payload })
                }
            }
        } catch let err as Error {
            completion( .failure(err))
        } catch let any {
            let err = Error(code: 500, message: any.localizedDescription)
            completion( .failure(err))
        }
    }


    @available(iOS 13.0, macOS 10.15, watchOS 6.0, tvOS 13.0, *)
    private final func run<Q, R>(query: Q) async throws -> R where Q: Codable, R: Codable {
        let dto = DTO(query, encoder: self.encoder)
        return try await withCheckedThrowingContinuation { continuation in
            do {
                try self.send(query: dto) { result in
                    if let error = try? self.decoder.decode(DTO<Error>.self, from: result) {
                        continuation.resume(with: .failure(error.payload))
                    } else {
                        let response = self.decoder.tryDecode(DTO<R>.self, from: result)
                        continuation.resume(with: response.map { $0.payload })
                    }
                }
            } catch let err as Error {
                continuation.resume(with: .failure(err))
            } catch let any {
                let err = Error(code: 500, message: any.localizedDescription)
                continuation.resume(with: .failure(err))
            }
        }
    }
}
```

Yes — it is `withCheckedThrowingContinuation`. Facts that follow from the code above:

- **Double-resume:** not reachable through `TDLibClient`, because `TDLibClient.send` never throws (its whole body is `queryQueue.async { … try! … }`), so the `catch` arms are dead code and the completion fires at most once (`completionHandler` does `removeValue` before invoking). It *would* be reachable for any other `TDLibApi` subclass whose `send` registers the completion and *then* throws — that crashes with "resumed multiple times".
- **Never-resumed (the real risk):** the completion lives only in `client.awaitingCompletions`. If the client is dropped from `TDLibClientManager.clients` (i.e. `authorizationStateClosed` arrives) or the manager's receive loop stops, in-flight entries are never invoked and every awaiting `try await` **hangs forever**. There is no timeout anywhere. TDTransport should wrap calls in its own timeout / cancellation.
- **Cancellation:** `withCheckedThrowingContinuation` (not `…WithCancellationHandler`), so Swift task cancellation does nothing — a cancelled Task still blocks until TDLib replies.
- **Retain cycle:** the async overload captures `self` **strongly** inside the completion (the completion-based overload uses `[weak self]`). Since that closure is stored in the client's own `awaitingCompletions`, an unanswered request keeps the `TDLibClient` alive indefinitely.
- **Shared `decoder`:** one `JSONDecoder` instance is used concurrently from the client's serial `updateHandlerQueue` — safe in practice here because all completions run on that one serial queue, but Swift 6 will see a non-`Sendable` class crossing isolation.
- **Error sniffing is untyped:** `decoder.decode(DTO<Error>.self, …)` succeeds on any payload with `code: Int` + `message: String`; `DTO.init(from:)` reads `@type` but never validates it. A legitimate response shaped like that would be surfaced as a thrown `TDLibKit.Error`.

- `TDLibClient`, `TDLibClientManager`, `ConcurrentDictionary`, `DTO`, `JSONDecoder`/`JSONEncoder` are non-`Sendable` reference types. `TDLibClient` in particular cannot cross an isolation boundary — but `createClient`'s `updateHandler` signature is `(Data, TDLibClient) -> Void`, i.e. it *hands you a `TDLibClient` on the client's own dispatch queue*. - One notable absence to flag: **there is no `Sources/TDLibKit/Generated/Models/UpdateAuthorizationState.swift`** (nor separate files for the other 183 update payloads) — everything `Update`-related lives in `Update.swift`. `ls Generated/Models | grep -i update` will mislead you.

### Reality differs from the common mental model

- **Parameter labels are alphabetical, not TL order.** Three separate slices flagged this as a compile-error trap: `searchChats(limit:query:typeFilter:)`, `getChatHistory(chatId:fromMessageId:limit:offset:onlyLocal:)`, `downloadFile(fileId:limit:offset:priority:synchronous:)`, `getRemoteFile(fileType:remoteFileId:)`, `sendChatAction(action:businessConnectionId:chatId:topicId:)`. Copy the signatures literally.
- **`sendMessage` gained `topicId`, and it is `MessageTopic?`** — an enum, not an `Int64` thread id. A plain 1-1 send passes `topicId: nil`.
- **`inputMessagePhoto` nests an `InputPhoto`** (and `inputMessageDocument` nests an `InputDocument`). The old flat `InputMessagePhoto(photo:width:height:…)` shape no longer compiles.
- **`TdClientImpl`, `TdApi` and `Logger` are the deprecated-or-alternate surface.** The live path is `TDLibClientManager.createClient` → `TDLibClient` (a `TDLibApi` subclass); `Logger` is deprecated in favour of `TDLibLogger` but still exists, and `TdClientImpl` still takes the deprecated one.
- **"Everything is Optional" does not mean "everything is omittable".** Request parameters are non-defaulted Optionals, so `setTdlibParameters` requires all 14 arguments at every call site. Conversely `PhoneNumberAuthenticationSettings` is a *model*: six of its seven fields are non-Optional and a partial init will not compile.
- **`TDLibKit.Error` conforms to `Swift.Error` and shadows it.** In any file importing TDLibKit, unqualified `Error` is the struct — which is why the generated code writes `Swift.Error` everywhere.
- **`ChatPosition.order` is `TdInt64`, decoded from a JSON string** — sort on `.rawValue`. And `order == 0` means *remove the chat from that list*, not "sort it last".
- **`Chat.chatLists` and `Chat.positions` are independent axes.** The doc states a chat can hold a non-zero position in a list it does not belong to, and belong to a list with no position in it.
- **`loadChats` signals end-of-list with a 404 error**, not an empty result. The paging loop must treat 404 as success-terminal.
- **`Messages.messages` is `[Message]?`** — a nullable list, not an empty array.
- **`MessageSendOptions.sendingId` is `Int`** — not `Int64`, not `TdInt64` — and it is the whole send-correlation mechanism, echoed back as `messageSendingStatePending.sendingId`.
- **There is no fixed code length.** 7 of `AuthenticationCodeType`'s 10 cases carry `length`; `SmsWord`, `SmsPhrase` and `FlashCall` do not (word / phrase / auto-filled pattern), and `EmailAddressAuthenticationCodeInfo.length` may be `0` for unknown. Nothing in these sources implies 5.
- **`checkAuthenticationEmailCode` takes an `EmailAddressAuthentication` enum, not a `String`**, and `resendAuthenticationCode` is not no-arg — it takes `ResendCodeReason?`.
- **`updateFile` is the upload-progress channel too.** There is no separate upload update: read `file.local.*` for downloads and `file.remote.isUploadingActive/isUploadingCompleted/uploadedSize` for uploads off the same stream.
- **`File.id` carries no documented lifetime guarantee at all.** The folklore "the id becomes invalid after restart" appears nowhere in the sources — the only written promises are on `RemoteFile.id` ("across application restarts or even from other devices") and `RemoteFile.uniqueId` ("persistent over time"). Persist those, and treat `File.id` as session-scoped by absence of a guarantee.
- **`preliminaryUploadFile` is not the normal send path** — its own doc says "In all other cases there is no need to preliminary upload a file"; it exists for voice and video notes being recorded.
- **`deinit → closeClients()` cannot terminate.** Swift zeroes `weak` references before `deinit` runs, so the `[weak self]` receive loop and `queryResultAsync` both bail and nothing ever removes a client — the `while (!self.clients.isEmpty) {}` spin never ends. `closeClients()` must be called explicitly while the manager is still strongly held, and even the happy path is a 100%-CPU spin.
- **The async bridge has no timeout, no cancellation, and a strong self-capture.** `run(query:)` uses `withCheckedThrowingContinuation` (not the cancellation-handler variant), so a cancelled Task still blocks; a client dropped from `clients` strands its `awaitingCompletions` and every `await` on it hangs forever; and the captured `self` keeps the `TDLibClient` alive until the reply arrives.
- **`Update` decoding has no unknown-`@type` fallback.** `Kind` is a plain `String`-raw enum, so any update this TDLib build does not know throws a `DecodingError` — the transport must swallow decode failures on the update path rather than propagate them.
- **`Update` decodes straight from the raw `Data`** — no `DTO<…>` wrapper needed — but only with `keyDecodingStrategy = .convertFromSnakeCase` (which `client.decoder` already has).
- **`createClient` is not inert.** It immediately sends `getOption("version")` to activate the client, and `TDLibClientManager`'s `td_receive(10)` loop starts inside `init`, not in a separate `start()`.
- **Error detection is untyped.** `decoder.decode(DTO<Error>.self, …)` succeeds on any payload shaped `{ code: Int, message: String }` because `DTO.init(from:)` reads `@type` but never validates it — a legitimate response of that shape would be thrown as an error.
- **`DTO`'s `@type` is derived from `String(describing: T.self)`** (lower-camelised, with one hardcoded `["TdData": "data"]` remap), so any type-name mangling would silently emit a wrong `@type` rather than fail.
- **The package is `swift-tools-version:5.3`** — it always compiles in Swift 5 language mode no matter what NotchGram sets, so none of its public types gets implicit `Sendable`. NotchGram's Swift 6 strict-concurrency target must box the client or convert `Data` → its own `Sendable` domain types at the boundary.
- **`Supergroup.memberCount` is not always known** — the doc restricts the guarantee to objects received through a specific list of methods, which does **not** include `loadChats`.
- **`updateUnreadMessageCount` / `updateUnreadChatCount` are gated on the message database.** The notch badge only works if TDLib was configured with `useMessageDatabase: true`.
- **`getAuthorizationState` and `getFile` are offline methods.** The first is "for informational purposes only" (drive state from `updateAuthorizationState`); the second is a cache probe that never fetches bytes.
- **`messageRichMessage` is a second text-bearing content case** sitting right after `messageText`, and `editMessageText` explicitly accepts it — a text renderer that only handles `messageText` is incomplete.
- **`ChatFolderIcon.name` is a free-form `String`, not an enum**, and the folder's display name is `info.name.text.text` — a `FormattedText` two levels down.
- **Id widths are inconsistent.** `secretChatId` and `chatFolderId` are `Int` while chat, user, supergroup and message ids in the same neighbourhood are `Int64`, and several fields (`ChatPosition.order`, `soundId`, `mediaAlbumId`, `effectId`, custom-emoji ids) are `TdInt64` string-encoded wrappers.
